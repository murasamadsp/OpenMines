# OpenMines Target Architecture Plan (The "Once and For All" Redesign)

Этот документ описывает целевую архитектуру игрового сервера OpenMines. План решает проблему размытых границ ECS и частых блокировок симулятора путем физического разделения сервера на изолированные крейты, гарантирующие соблюдение архитектурных границ на уровне компилятора Rust.

---

## 1. Проблема текущей архитектуры: "Over-segmented Bottom, Bloated Top"

Текущая кодовая база имеет избыточное деление на мелкие библиотеки внизу (`core`, `config`, `world`, `storage`), но при этом сам `openmines-server` является монолитом, в котором смешаны:
* Сетевой слой (TCP-сессии игроков, парсинг сырых пакетов).
* Веб-интерфейс API (веб-карта, статистика, админка).
* Игровая симуляция (Bevy ECS, системы, программатор, ивенты).
* Инфраструктура (потоки симулятора, презентации и сохранения).

Из-за этого ECS (`bevy_ecs::World`) лежит под общим `RwLock<EcsWorld>`, за который постоянно конкурируют сетевые хэндлеры сессий, веб-руты и поток симуляции. Это гарантирует **недетерминированность** (порядок мутаций зависит от планировщика ОС) и **просадки кадров** (stalls / OVER-BUDGET тики).

---

## 2. Целевая модель: Crates-Level Boundary Isolation

Мы переходим к физической изоляции слоев. Крейт `openmines-server` разбивается на три вложенных суб-крейта:

```text
                           ┌───────────────────────────────┐
                           │      openmines-server         │
                           │   (App runner, main.rs)       │
                           └───────────────┬───────────────┘
                                           │
                    ┌──────────────────────┴──────────────────────┐
                    ▼                                             ▼
     ┌───────────────────────────────┐             ┌───────────────────────────────┐
     │   openmines-server-network    │             │  openmines-server-simulation  │
     │     (TCP, Axum Web-API)       │             │   (Bevy ECS, Game Logic)      │
     └──────────────┬────────────────┘             └──────────────┬────────────────┘
                    │                                             │
                    │         QueuedGameCommand                   │
                    │────────────────────────────────────────────►│  (ECS скрыт внутри)
                    │                                             │
                    │◄────────────────────────────────────────────│
                    │             GameEvent / WebSnapshot         │
                    └─────────────────────────────────────────────┘
```

### 2.1. Крейт `openmines-server-simulation` (Ядро игры)
* **Назначение**: Единственный владелец ECS (`bevy_ecs::World`). Обрабатывает тики, выполняет симуляцию, рассчитывает физику песка, управляет программатором.
* **Изоляция**: `bevy_ecs::World` лежит внутри структуры `SimulationRuntime` **по значению** (без `RwLock` и `Arc`). Доступ к нему извне физически закрыт.
* **Зависимости**: `openmines-world`, `openmines-storage`, `bevy_ecs`, `dotnet-rng`.
* **Dependencies на сеть**: Отсутствуют. В этом крейте нет упоминания `tokio::net`, `axum` или сетевых сокетов.

### 2.2. Крейт `openmines-server-network` (Сетевой/API слой)
* **Назначение**: Прием TCP-соединений, управление сессиями (`SessionHub`), сериализация пакетов протокола, хостинг веб-интерфейса Axum.
* **Изоляция**: **Не зависит от `bevy_ecs`**. Крейт вообще не импортирует ECS-модули. Он общается с симуляцией исключительно через типизированные каналы (команды) и читает неизменяемый `WebSnapshot`.
* **Зависимости**: `openmines-protocol`, `openmines-server-simulation` (только типы команд и событий), `axum`, `tokio`.

### 2.3. Крейт `openmines-server` (Точка входа)
* **Назначение**: Оркестрация. Запускает приложение.
* **Логика**:
  1. Инициализирует каналы связи (`mpsc::channel` для команд симуляции).
  2. Запускает поток симуляции (`simulation::run`).
  3. Передает Sender команд и Reader снимков в сетевой слой и запускает его (`network::run`).

## 3. Схема взаимодействия и потоки данных

Вся работа сервера подчиняется строгому однонаправленному потоку данных:

```text
[Клиент (TCP)] 
      │ (Сырой пакет)
      ▼
[network::Session] 
      │ (Парсинг пакета)
      ▼
[QueuedGameCommand] ────────► [Simulation Channel]
                                      │
                                      ▼
                            [Simulation Thread]
                                      │ (Эксклюзивный ecs-write внутри тика)
                                      ▼
                            [Apply Game Logic] 
                                      │
                                      ├────────────────────────┐
                                      ▼                        ▼
                                 [GameEvent]             [SaveCommand]
                                      │                        │
                                      ▼                        ▼
                            [Presentation Thread]     [Persistence Thread]
                                      │                        │
                                      ▼                        ▼
                               [TCP Outbox]               [SQLite DB]
```

### 3.1. Чтение данных (Snapshot Pattern)
Для отдачи карты, статистики или UI, которые раньше лезли в ECS:
1. Симулятор в конце кадра генерирует иммутабельный снимок состояния (например, `Arc<WebSnapshot>` или `Arc<PlayerSnapshot>`).
2. Сетевой слой и веб-руты читают этот `Arc` без блокировок. Чтение происходит за $O(1)$ и не мешает симулятору выполнять вычисления.

## 4. Поэтапный план миграции (Zero-Downtime Migration)

Чтобы не сломать сборку 500 файлов за раз, переход выполняется по шагам:

### Этап 1: Внедрение компиляторного барьера (Baseline Allow-list)
1. В `AGENTS.md` прописывается жесткое правило: *"Запрещено добавлять новые прямые обращения к ECS в модули сессий"*.
2. В `scripts/arch-guard.sh` добавляется проверка соответствия текущего архитектурного долга файлу исключений `docs/reference/ecs_bypass_baseline.txt`. С этого момента автоматика начинает блокировать любой новый "говнокод".

### Этап 2: Постепенный перенос хэндлеров на команды
Один за другим переписываются логические блоки (GUI Рынка, Кланы, UI Программатора, Движение) по паттерну:
* Из сетевого хэндлера удаляется `.ecs.read()` / `.ecs.write()`.
* Вместо этого формируется команда и отправляется в `QueuedGameCommand`.
* Соответствующие строки удаляются из `ecs_bypass_baseline.txt`.

### Этап 3: Физическое разделение на крейты
Когда файл `ecs_bypass_baseline.txt` становится пустым (все прямые обращения удалены):
1. В `GameState` у поля `ecs` убирается модификатор `pub`.
2. Создаются папки `crates/server/openmines-server/simulation` и `crates/server/openmines-server/network`.
3. Код физически разносится по крейтам. `bevy_ecs` удаляется из зависимостей крейта `network`.

---

## 5. Что это даст проекту?

1. **Гарантированный детерминизм**: Симулятор полностью изолирован от внешнего сетевого влияния. Игру можно перезапустить с любого сида и лога команд, и состояние мира сойдется 1:1. Это делает возможным offline fast-forward (промотку 8 часов оффлайна без нагрузки на CPU).
2. **Нулевой Lock Contention**: Сетевой и веб-слои больше не конкурируют с симулятором за память ECS. Презентационные тики и веб-запросы к статистике больше не вызовут задержек симуляции.
3. **Чистый код**: Устраняется "двойная бухгалтерия" (когда сущности пишутся и в ECS, и вручную в DashMap). Все индексы переносятся внутрь ECS в виде ресурсов Bevy, так как симулятор владеет миром монопольно.
